# API Reference

ConvexBooking exposes two API layers following the **trust zones pattern**: a **Public API** for the anonymous booking flow, and an **Admin API** for management operations.

<Callout type="info" title="What “Public” and “Admin” mean here">
  These labels are **not** properties of the `@mrfinch/booking` component — the component never calls `ctx.auth` and cannot tell callers apart. They describe the **gateway** your app puts in front of it, i.e. which custom function builder a wrapper is written with.

  On this sandbox the gateway is drawn like this: **booking is fully anonymous** (no sign-in, ever — the booker is passed in with the mutation), and **the dashboard is behind a login** ("Continue as guest admin" — Convex Auth v2 with the anonymous provider). Your own deployment can draw the line somewhere else: same component functions, different builders.
</Callout>

## Setup

ConvexBooking uses a **gateway pattern**: authentication and authorization live in your app's wrapper functions, never inside the component. That keeps the component reusable and lets you choose any provider — or none.

### Step 1: Create Custom Function Builders

`convex/functions.ts` defines the four builders every wrapper is written with. This is the sandbox's real file:

```typescript title="convex/functions.ts"
import {
  customQuery,
  customMutation,
  customCtx,
} from "convex-helpers/server/customFunctions";
import { query, mutation } from "./_generated/server";
import type { QueryCtx, MutationCtx } from "./_generated/server";
import { ConvexError } from "convex/values";

export type UserIdentity = {
  /** Convex Auth user id (`identity.subject`) — the app `users` row. */
  userId: string;
  /** Always "" for anonymous sessions; kept for admin.ts compatibility. */
  email: string;
  name?: string;
};

/** Read the Convex Auth identity, or null when the caller is not signed in. */
export async function getUserIdentity(
  ctx: QueryCtx | MutationCtx
): Promise<UserIdentity | null> {
  const identity = await ctx.auth.getUserIdentity();
  if (!identity) return null;
  return {
    userId: identity.subject,
    email: identity.email ?? "",
    name: identity.name,
  };
}

/** Require a signed-in (guest admin) session. */
export async function requireAuth(
  ctx: QueryCtx | MutationCtx
): Promise<UserIdentity> {
  const user = await getUserIdentity(ctx);
  if (!user) {
    throw new ConvexError({
      code: "UNAUTHENTICATED",
      message: "Sign in as guest admin to use the dashboard",
    });
  }
  return user;
}

// Public — no auth, nothing injected (availability, browsing, booking, presence).
export const publicQuery = customQuery(query, customCtx(async () => ({})));
export const publicMutation = customMutation(mutation, customCtx(async () => ({})));

// Admin — requires a Convex Auth identity; injects { user, role }.
export const adminQuery = customQuery(
  query,
  customCtx(async (ctx) => {
    const user = await requireAuth(ctx);
    return { user, role: "admin" as const };
  })
);

export const adminMutation = customMutation(
  mutation,
  customCtx(async (ctx) => {
    const user = await requireAuth(ctx);
    return { user, role: "admin" as const };
  })
);
```

<Callout type="tip">
  The builder **names** are the contract, not their contents. Swapping the sandbox's anonymous `publicMutation` for one that calls `requireAuth` turns booking into a signed-in-only flow without touching a single wrapper.
</Callout>

### Step 2: Create Public API Gateway

`convex/public.ts` exposes the visitor-facing endpoints. Two jobs beyond passing arguments through: it makes availability **schedule-aware on the server**, and it **guards** booking writes (the component deliberately leaves host policy to the caller).

```typescript title="convex/public.ts"
import { v, ConvexError } from "convex/values";
import { components } from "./_generated/api";
import { publicQuery, publicMutation } from "./functions";

// Resource browsing (anonymous)
export const listResources = publicQuery({
  args: { organizationId: v.string(), type: v.optional(v.string()) },
  handler: async (ctx, args) => {
    return await ctx.runQuery(components.booking.resources.listResources, {
      ...args,
      activeOnly: true,
    });
  },
});

// Day slots (anonymous) — the Booker only sends resourceId/date/eventLength,
// so the wrapper resolves the schedule and passes the 0.3.0 arguments itself.
export const getDaySlots = publicQuery({
  args: {
    resourceId: v.string(),
    date: v.string(),
    eventLength: v.number(),
    slotInterval: v.optional(v.number()),
    eventTypeId: v.optional(v.string()),
    excludeBookingUid: v.optional(v.string()),
  },
  handler: async (ctx, args) => {
    const avail = await resolveAvailabilityContext(ctx, args.resourceId, {
      eventTypeId: args.eventTypeId,
    });
    if (!avail) return [];
    // … past-day / horizon / min-notice filtering, then offeredDaySlots()
  },
});

// Create booking (anonymous, booker is REQUIRED)
export const createBooking = publicMutation({
  args: {
    eventTypeId: v.string(),
    resourceId: v.string(),
    start: v.number(),
    end: v.number(),
    timezone: v.string(),
    booker: v.object({
      name: v.string(),
      email: v.string(),
      phone: v.optional(v.string()),
      notes: v.optional(v.string()),
    }),
    location: v.object({ type: v.string(), value: v.optional(v.string()) }),
  },
  handler: async (ctx, args) => {
    assertBookableRange(args.start, args.end);          // 15-minute grid, end > start
    const booker = sanitizeBooker(args.booker);          // trim + length + email checks
    const location = { type: args.location.type, value: args.location.value?.slice(0, 300) };
    const eventType = await loadBookableEventType(ctx, args.eventTypeId);
    const resource = await loadBookableResource(ctx, args.resourceId, args.eventTypeId);
    const duration = assertAllowedDuration(eventType, args.start, args.end);
    assertBookingWindow(eventType, args.start, Date.now()); // past / notice / horizon
    await assertStartIsOfferedSlot(ctx, { resource, eventType, start: args.start, durationMinutes: duration });
    await enforceBookingRateLimit(ctx, booker.email);    // 5 per email per 10 minutes

    try {
      return await ctx.runMutation(components.booking.public.createBooking, {
        ...args,
        booker,   // sanitized
        location, // trimmed
        resendOptions: resendOptions(),
      });
    } catch (error) {
      translateComponentError(error);                     // → ConvexError({ code, message })
    }
  },
});
```

### Step 3: Create Admin API Gateway

`convex/admin.ts` wraps the management surface with `adminQuery` / `adminMutation`, so every one of them requires a session and gets `{ user, role }` injected:

```typescript title="convex/admin.ts"
import { v } from "convex/values";
import { components } from "./_generated/api";
import { adminQuery, adminMutation } from "./functions";

// List all resources (including inactive)
export const listResources = adminQuery({
  args: {
    organizationId: v.string(),
    type: v.optional(v.string()),
    activeOnly: v.optional(v.boolean()),
  },
  handler: async (ctx, args) => {
    return await ctx.runQuery(components.booking.resources.listResources, args);
  },
});

// Transition a booking — the injected identity becomes the audit trail
export const transitionBookingState = adminMutation({
  args: {
    bookingId: v.string(),
    toStatus: v.string(),
    reason: v.optional(v.string()),
  },
  handler: async (ctx, args) => {
    const { user } = ctx; // injected by adminMutation
    return await ctx.runMutation(components.booking.hooks.transitionBookingState, {
      bookingId: args.bookingId as any,
      toStatus: args.toStatus,
      reason: args.reason,
      changedBy: user.userId, // Track who made the change
      resendOptions: process.env.RESEND_API_KEY ? { /* … */ } : undefined,
    });
  },
});
```

### Why This Pattern?

**Trust Zones**: the public gateway serves the whole booking flow to anonymous visitors; the admin gateway requires a session before anything can be created, edited or deleted.

**Defense-in-Depth**: policy that the component cannot know about — opening hours, minimum notice, duration whitelists, rate limits — is enforced in the wrapper before the component is ever called.

**Flexibility**: you own the auth logic. This sandbox uses Convex Auth v2's anonymous provider; a production app swaps in Clerk, WorkOS, Auth0 or a custom JWT and changes nothing else.

## Public API

The Public API (`convex/public.ts`) handles the customer-facing booking flow. Every function in it is written with `publicQuery` / `publicMutation`: **no identity is read and none is required** — browsing, availability, presence and booking all work for an anonymous visitor. What protects it is not a login but the guard in each wrapper.

### Availability Queries

Check what time slots are available for booking.

#### `getMonthAvailability`

Get availability dots for the calendar month view. Returns a map of dates to boolean availability.

```typescript
const availability = await ctx.runQuery(api.public.getMonthAvailability, {
  resourceId: "studio-a",
  dateFrom: "2026-03-01",
  dateTo: "2026-03-31",
  eventLength: 60,               // Duration in minutes
  slotInterval: 60,              // Optional: time between slots
  eventTypeId: "studio-session", // Optional: narrows schedule + booking window
  excludeBookingUid: "bk_17…",   // Optional: reschedule flow (see below)
});
// Returns: { "2026-03-15": true, "2026-03-16": false, … }
```

**Parameters:**
- `resourceId` (string): ID of the resource to check
- `dateFrom` (string): ISO date string for start of range
- `dateTo` (string): ISO date string for end of range
- `eventLength` (number): Duration of booking in minutes
- `slotInterval` (number, optional): Time between available slots
- `eventTypeId` (string, optional): Use this event type's schedule and notice/horizon window
- `excludeBookingUid` (string, optional): Treat that booking's own slots as free

**Returns:** `Record<string, boolean>` — map of ISO dates to availability

**Behaviour of the sandbox wrapper:** malformed input returns `{}` (never an error), ranges longer than 62 days are rejected, past days and days beyond the booking horizon are forced to `false`, and the resource's schedule is resolved server-side before the component is called.

**Use Case:** showing calendar dots indicating which days have availability.

---

#### `getDaySlots`

Get detailed time slots for a specific day.

```typescript
const slots = await ctx.runQuery(api.public.getDaySlots, {
  resourceId: "studio-a",
  date: "2026-03-15",
  eventLength: 60,               // Booking duration
  slotInterval: 30,              // Optional: show slots every 30 minutes
  eventTypeId: "studio-session", // Optional
  excludeBookingUid: "bk_17…",   // Optional
});
// Returns: [{ time: "2026-03-15T09:00:00.000Z" }, { time: "2026-03-15T09:30:00.000Z" }, … ]
```

**Parameters:**
- `resourceId` (string): ID of the resource
- `date` (string): ISO date string (YYYY-MM-DD), interpreted in the schedule's timezone
- `eventLength` (number): Duration in minutes
- `slotInterval` (number, optional): Interval between slots
- `eventTypeId` (string, optional): Use this event type's schedule and windows
- `excludeBookingUid` (string, optional): Treat that booking's own slots as free

**Returns:** array of slot objects (`{ time }`) — the same list `createBooking` validates against

**Behaviour of the sandbox wrapper:** a day in the past, a day beyond the horizon or a malformed argument returns `[]`; slots inside the minimum-notice window are filtered out, so what the picker shows is exactly what the booking guard accepts.

#### Schedule-aware availability (0.3.0)

Both queries take optional 0.3.0 arguments at the **component** boundary. The React `Booker` never sends them — the wrapper resolves the resource, finds the schedule (the event type's `scheduleId`, else the organization's `getDefaultSchedule`) and fills them in:

```typescript title="convex/public.ts (month view)"
await ctx.runQuery(components.booking.public.getMonthAvailability, {
  resourceId: args.resourceId,
  dateFrom: args.dateFrom,
  dateTo: toIsoDateUtc(effectiveTo),
  eventLength: args.eventLength,
  slotInterval:
    args.slotInterval ??
    (avail.eventType ? effectiveSlotInterval(avail.eventType) : undefined),
  // Both or neither — otherwise the component silently takes the legacy path.
  resourceTimezone: avail.scheduleId ? avail.timezone : undefined,
  scheduleId: avail.scheduleId,
  excludeBookingUid: sanitizeUid(args.excludeBookingUid),
});
```

```typescript title="convex/public.ts (day view)"
let availableSlots: number[] | undefined;
if (avail.scheduleId && avail.timezone) {
  const effective = await ctx.runQuery(
    components.booking.schedules.getEffectiveAvailability,
    { scheduleId: avail.scheduleId, date: opts.date }
  );
  availableSlots = effective.availableSlots;
  // Empty window (weekend, "unavailable" override): no slots, skip the call.
  if (availableSlots.length === 0) return [];
}

await ctx.runQuery(components.booking.public.getDaySlots, {
  resourceId: avail.resource.id,
  date: opts.date,
  eventLength: opts.eventLength,
  slotInterval: opts.slotInterval,
  resourceTimezone: availableSlots ? avail.timezone : undefined,
  availableSlots,
  excludeBookingUid: opts.excludeBookingUid,
});
```

**`getMonthAvailability` (component) — optional arguments:**
- `resourceTimezone` (string): IANA timezone the schedule is expressed in
- `scheduleId` (string): the schedule's **external** id (`schedule.id`, not the Convex document id); the component computes the effective window per day itself
- `excludeBookingUid` (string): treat that booking's own slots as free

**`getDaySlots` (component) — optional arguments:**
- `resourceTimezone` (string): IANA timezone of `availableSlots`
- `availableSlots` (number[]): the 15-minute slot indices for that day, i.e. `schedules.getEffectiveAvailability({ scheduleId, date }).availableSlots`
- `excludeBookingUid` (string): treat that booking's own slots as free

<Callout type="warning" title="resourceTimezone must accompany the others">
  The schedule-aware path only runs when `resourceTimezone` **and** its partner argument are both present — `scheduleId` for the month view, `availableSlots` for the day view. With only one of the pair the component **silently** falls back to its legacy hardcoded 09:00–17:00 UTC business hours instead of raising an error, and the month view and the day view start disagreeing. Pass both or neither.
</Callout>

**`excludeBookingUid` semantics:** the named booking's slots are subtracted from the busy set, so a reschedule UI can show the booking's current time as free. It is **ignored** for an unknown uid, for a booking on another resource, and for a booking whose status is not `pending`, `confirmed` or `provisional` — a cancelled booking already released its slots, and excluding it again would hand out someone else's slots. It applies to the non-fungible slot bitmap only, not to pooled (`isFungible`) quantity.

#### `getEffectiveAvailability`

Get the effective availability window of a schedule for one date — weekly hours plus any date override.

```typescript
const effective = await ctx.runQuery(api.public.getEffectiveAvailability, {
  scheduleId: "business-hours", // external schedule id
  date: "2026-03-15",
});
// Returns: { availableSlots: [36, 37, 38, …] }  // 15-minute slot indices, 0–95
```

**Returns:** `{ availableSlots: number[] }` — local slot indices (`hour * 4 + minute / 15`). An `"unavailable"` override or a day without weekly hours yields `[]`. An **unknown** `scheduleId` falls back to slots 36–67 (09:00–17:00).

**Use Case:** feeding `getDaySlots`'s `availableSlots` argument, and rendering opening hours.

---

#### `getAvailability`

Check if a specific time range collides with an existing booking. Ignores opening hours — this is a raw slot-collision check, not a UI availability source.

```typescript
const isAvailable = await ctx.runQuery(api.public.getAvailability, {
  resourceId: "studio-a",
  start: 1773558000000, // Unix timestamp (ms)
  end: 1773561600000,   // Unix timestamp (ms)
});
// Returns: true | false
```

**Parameters:**
- `resourceId` (string): ID of the resource
- `start` (number): Unix timestamp in milliseconds
- `end` (number): Unix timestamp in milliseconds

**Returns:** `boolean` — whether the slots in the range are free

### Presence System

Real-time slot locking to prevent double-booking during selection. Presence is keyed by a **client-generated session id**, not by a user — it works for anonymous visitors and survives the hourly sandbox reset (the wipes leave presence alone; holds expire on their own).

#### `getDatePresence`

Get all active presence holds for a date. Used by the frontend to filter out slots being selected by other visitors.

```typescript
const presence = await ctx.runQuery(api.public.getDatePresence, {
  resourceId: "studio-a",
  date: "2026-03-15",
});
// Returns: [
//   { slot: "2026-03-15T10:00:00.000Z", user: "session-abc123" },
//   …
// ]
```

**Parameters:**
- `resourceId` (string): Resource ID
- `date` (string): ISO date string (YYYY-MM-DD)

**Returns:** array of presence objects showing which slots are held

**Use Case:** the frontend filters out reserved slots and shows them as "Reserved" to other users.

---

#### `heartbeat`

Maintain a slot hold by sending periodic heartbeats. Called every 5 seconds while a visitor is selecting a slot.

```typescript
await ctx.runMutation(api.public.heartbeat, {
  resourceId: "studio-a",
  slots: ["2026-03-15T10:00:00.000Z", "2026-03-15T11:00:00.000Z"],
  user: "session-abc123", // Client-generated session ID
});
```

**Parameters:**
- `resourceId` (string): Resource ID
- `slots` (string[]): Array of ISO timestamp strings to hold (max 32 per call — more throws `TOO_MANY_SLOTS`)
- `user` (string): Client-generated unique session ID

**Note:** holds expire after 10 seconds of inactivity. The frontend hook handles this automatically. Holds are keyed per `(user, slot, resourceId)`, so the same session can hold the same time on two resources (0.3.0 fix).

### Booking Mutations

Create and retrieve bookings.

#### `createBooking`

Create a new booking as an anonymous visitor.

<Callout type="info" title="No sign-in — but a required booker">
  Booking on this sandbox never asks for a login. Because there is no identity to read the name and email from, `booker` is a **required** argument: the `Booker` form always sends it. Everything that used to be enforced by "you must be signed in" is enforced by the guard below instead.
</Callout>

```typescript
const booking = await ctx.runMutation(api.public.createBooking, {
  eventTypeId: "studio-session",
  resourceId: "studio-a",
  start: 1773558000000,  // Unix timestamp (ms), on the 15-minute grid
  end: 1773561600000,    // Unix timestamp (ms)
  timezone: "Europe/Berlin",
  location: {
    type: "inPerson",
    value: "123 Main St", // Optional
  },
  booker: {               // REQUIRED
    name: "John Doe",
    email: "john@example.com",
    phone: "+1234567890",            // Optional
    notes: "Looking forward to it!", // Optional
  },
});
// Returns: { bookingId, uid, status, … }
```

**Parameters:**
- `eventTypeId` (string): ID of the event type
- `resourceId` (string): ID of the resource to book
- `start` (number): Unix timestamp in milliseconds
- `end` (number): Unix timestamp in milliseconds
- `timezone` (string): IANA timezone (e.g. "Europe/Berlin")
- `location` (object): `{ type, value? }`
- `booker` (object, **required**): `{ name, email, phone?, notes? }`

**Returns:** booking object with `bookingId`, `uid` (confirmation code) and `status`

**Guard order** (each failure is a `ConvexError({ code, message })`, never a redacted "Server Error"):

1. Times on the 15-minute grid, `end > start` — `SLOT_NOT_ALIGNED`, `INVALID_RANGE`, `INVALID_TIME`
2. Known IANA timezone — `INVALID_TIMEZONE`
3. Booker name / email / phone / notes sane — `NAME_REQUIRED`, `NAME_TOO_LONG`, `INVALID_EMAIL`, `PHONE_TOO_LONG`, `NOTES_TOO_LONG`
4. Event type exists and is active — `EVENT_TYPE_NOT_FOUND`, `EVENT_TYPE_INACTIVE`
5. Resource exists, is active, is **standalone**, and is linked to the event type — `RESOURCE_NOT_FOUND`, `RESOURCE_INACTIVE`, `RESOURCE_NOT_STANDALONE`, `NOT_LINKED`
6. Duration is one of the event type's offered lengths — `INVALID_DURATION`
7. Not in the past, respects `minNoticeMinutes` and `maxFutureMinutes` — `IN_PAST`, `TOO_SOON`, `TOO_FAR_AHEAD`
8. `start` is one of the slots `getDaySlots` offers — schedule window, date overrides and collisions in one check — `SLOT_NOT_AVAILABLE`
9. Rate limit: 5 bookings per email per 10 minutes — `RATE_LIMITED`
10. The component write itself, with its errors translated — `SLOT_NOT_AVAILABLE`, `EVENT_TYPE_*`, `RESOURCE_*`, otherwise `BOOKING_FAILED`

**Behaviour:**
- Sends a confirmation email if `RESEND_API_KEY` is set (it is not, on this sandbox)
- Status is `confirmed` immediately, or `pending` when the event type sets `requiresConfirmation`
- The booking's `organizationId` is copied from the event type (0.3.0), so admin filters by organization find it

## Admin API

The Admin API (`convex/admin.ts`) provides management operations for resources, event types, schedules, date overrides and bookings. Every function is written with `adminQuery` / `adminMutation`.

<Callout type="warning" title="Session required">
  An `adminQuery` / `adminMutation` calls `ctx.auth.getUserIdentity()` and throws `ConvexError({ code: "UNAUTHENTICATED", message: "Sign in as guest admin to use the dashboard" })` when there is none. On this sandbox any visitor can obtain one with **"Continue as guest admin"** — the gate makes the dashboard an explicit, sessioned step and gives audit fields a user id; it does not make the data private. Everything here is shared, and the sandbox is wiped every hour.
</Callout>

### Resource Management

CRUD operations for resources.

#### `listResources`

List all resources, including inactive ones.

```typescript
const resources = await ctx.runQuery(api.admin.listResources, {
  organizationId: "demo-org",
  type: "room",      // Optional filter
  activeOnly: false, // Show inactive resources
});
```

#### Add-on resources: `isStandalone` (enforced since 0.3.0)

`isStandalone: false` marks a resource that may only be booked **together with** a standalone one — rental equipment, an engineer, a backline package. Before 0.3.0 the flag was advisory; the component now enforces it:

- `createBooking` and `createProvisionalBooking` reject a lone add-on with
  `Resource "gear-01" cannot be booked alone (isStandalone: false)`.
  The sandbox's `convex/public.ts` translates that to `ConvexError({ code: "RESOURCE_NOT_STANDALONE", message: "This resource can only be booked as an add-on." })` and, because its own guard checks the flag first, usually raises it before the component is called.
- `createMultiResourceBooking` requires **at least one** standalone resource in the list, otherwise
  `Resource "gear-01", "gear-02" cannot be booked alone (isStandalone: false): add a standalone resource to the booking`.
  An empty resource list is rejected too (it used to be a `TypeError`).
- Resources with no document at all count as standalone.

Add-ons are still listed by `listResources`, so filter them out of your booking UI with `isStandalone !== false`.

#### Schedule validation rules (0.3.0)

Before 0.3.0 the component accepted any strings: `timeToSlot("garbage")` produced `NaN` and the day silently read as an **empty window**, so a typo turned into "nothing is bookable, no error anywhere". Time windows are now validated at the component boundary — in `createSchedule`, in `updateSchedule` (only when the patch contains `weeklyHours`), in `createDateOverride` and in `updateDateOverride` (only when the patch contains `customHours`).

The rules, with the exact messages the component throws:

- `startTime` / `endTime` must match `HH:MM` between `00:00` and `23:59` —
  `Invalid weeklyHours (dayOfWeek 1) startTime "9:00": expected "HH:MM" between 00:00 and 23:59`
- minutes must sit on the 15-minute grid (`00`, `15`, `30`, `45`), the component's slot size —
  `Invalid weeklyHours (dayOfWeek 1) endTime "17:20": minutes must be on the 15-minute grid (00, 15, 30, 45)`
- `startTime` must be strictly before `endTime` —
  `Invalid weeklyHours (dayOfWeek 1) window: startTime "18:00" must be before endTime "09:00"`
- `dayOfWeek` must be an integer between `0` (Sunday) and `6` (Saturday) —
  `Invalid weeklyHours dayOfWeek 7: expected an integer between 0 (Sunday) and 6 (Saturday)`
- windows of the **same** day must not overlap; adjacent windows sharing a boundary (…–12:00 + 12:00–…) are fine —
  `Overlapping weeklyHours (dayOfWeek 1) windows: 09:00–13:00 and 12:00–18:00`

Date overrides are validated with the same code and the label `customHours`, e.g.
`Invalid customHours startTime "25:00": expected "HH:MM" between 00:00 and 23:59` and
`Overlapping customHours windows: 10:00–14:00 and 13:00–16:00`.

<Callout type="warning" title="Upgrading from 0.2.x">
  These writes used to be accepted. Check seed scripts and admin forms before upgrading — a schedule that "worked" with `"9:00"` or a 20-minute boundary now throws on write.
</Callout>

Split shifts are supported: two windows on one day (08:00–12:00 and 14:00–17:30) each anchor their own slot grid, so a 150-minute event offers 08:00 **and** 14:00.

<Callout type="tip" title="cancelled and declined release the slots (0.3.0)">

</Callout>

**Note:** transitions are recorded in `booking_history` with `changedBy` — the injected `user.userId`, i.e. the guest-admin session that made the change. The matching hook (`booking.confirmed`, `booking.cancelled`, `booking.declined`) fires afterwards and sends an email when Resend is configured.

## Maintenance & Sandbox Resets

The component's tables are **isolated** from the host app — your own `ctx.db` cannot read or delete a single row of them. Demo sandboxes, seed scripts and test fixtures therefore need reset functions *inside* the component. 0.3.0 adds three, exposed through the client wrapper.

#### `wipeAllBookingData`

Deletes `bookings`, `booking_history`, `booking_items`, `daily_availability` and `quantity_availability`, and returns per-table counts. The **setup survives** — resources, schedules, date overrides, event types, resource ↔ event type links and hooks stay — so the calendar is empty but immediately bookable again.

```typescript
const counts = await ctx.runMutation(components.booking.maintenance.wipeAllBookingData, {});
// Returns: { bookings, bookingHistory, bookingItems, dailyAvailability, quantityAvailability }
```

**Use Case:** clearing a demo between runs, or freeing every slot without re-seeding.

---

#### `wipeAllData`

Everything `wipeAllBookingData` deletes, **plus** the setup tables (`date_overrides`, `resource_event_types`, `hooks`, `schedules`, `event_types`, `resources`), dependents first. Returns counts for all eleven tables.

```typescript
const counts = await ctx.runMutation(components.booking.maintenance.wipeAllData, {});
```

**Use Case:** re-seeding a sandbox from scratch. `createSchedule` / `createResource` throw on duplicate ids, so the wipe must run *before* the reseed.

**Presence is left alone by both wipes:** `presence` and `presence_heartbeats` are transient real-time locks holding references to scheduled functions, and they expire on their own within seconds.

---

#### `getDailyAvailability`

The raw slot occupancy of one resource/day — `getDaySlots` only reports the *free* slots and says nothing about what is booked.

```typescript
const busySlots = await ctx.runQuery(components.booking.maintenance.getDailyAvailability, {
  resourceId: "studio-a",
  date: "2026-03-15", // UTC date key
});
// Returns: [36, 37, 38, 39] — 15-minute slot indices — or null when no row exists
```

**Use Case:** verifying fixtures, and debugging a slot that refuses to free up.

---

#### Internal only

<Callout type="danger" title="Both wipes are unauthenticated at the component boundary">
  The component cannot know who your admins are, so it does not check. **Never re-export `wipeAllBookingData` / `wipeAllData` as public mutations.** On this site they are not reachable from `convex/public.ts` or `convex/admin.ts` at all — nothing a visitor or a guest admin can call resets anything. They are wrapped in `internalMutation` and driven by a cron.
</Callout>

```typescript title="convex/crons.ts"
import { cronJobs } from "convex/server";
import { internal } from "./_generated/api";

const crons = cronJobs();

// Public sandbox: wipe every booking + setup row, reseed the demo org and
// purge stale guest-admin users. Nothing public can trigger this.
crons.interval("reset sandbox", { hours: 1 }, internal.seed.resetSandbox, {});

export default crons;
```

```typescript title="convex/seed.ts"
/** Wipe every booking AND setup row. Internal only. */
export const wipeSandbox = internalMutation({
  args: {},
  returns: wipeResult,
  handler: async (ctx) => {
    return await ctx.runMutation(components.booking.maintenance.wipeAllData, {});
  },
});

/** Hourly sandbox reset: three separate mutations so a large wipe cannot drag
 *  the reseed into one oversized transaction. */
export const resetSandbox = internalAction({
  args: {},
  handler: async (ctx) => {
    const wiped = await ctx.runMutation(internal.seed.wipeSandbox, {});
    const seeded = await ctx.runMutation(internal.seed.seedDemoData, {});
    // … then cleanupGuestUsers() in batches: guest-admin `users` rows older
    // than an hour and expired booking rate-limit rows.
    return { wiped, seeded };
  },
});
```

**What the hourly reset does, in order:** `wipeAllData` (bookings *and* setup) → `seedDemoData` (one org, one Mon–Fri 09:00–18:00 Europe/Berlin schedule, four resources, two event types, their links) → `cleanupGuestUsers` (guest-admin rows older than 60 minutes, plus stale rate-limit rows). Guest sessions are not revoked — there is no per-user session API in the auth core — they simply expire.

<Callout type="info">
  Everything you create on this sandbox is shared with every other visitor and disappears within the hour. Booking uids, guest-admin sessions and dashboard edits are all temporary by design.
</Callout>
